## 目标与范围

完成本轮学习后，希望能够独立解释并验证三件事：一条查询为什么慢，一次并发更新为什么等待，以及提交后的数据如何保存、复制和恢复。

目标是形成 10 篇有实验依据的首轮笔记；公开发表前的打磨另计。按用户要求，不设学习时长或完成期限，时间充裕时继续推进；以理解与验证为完成标准。

本轮重点是单机 InnoDB 的执行、索引、事务、锁和日志。复制与恢复完成最小闭环；分库分表、完整高可用部署、JSON 多值索引、压缩与分区暂留扩展，避免同时铺开。

## 练习数据集

选择两个互补样例库：ClassicModels 贯穿业务学习，Employees 在索引与执行计划阶段补充数据规模。先导入第一个即可，不要求一开始同时熟悉两套模型。

### 主线：ClassicModels 订单与库存样例

- 发布方：[MySQLTutorial 样例库介绍与表关系](https://www.mysqltutorial.org/getting-started-with-mysql/mysql-sample-database/)。
- 获取：[SQL 压缩包](https://www.mysqltutorial.org/wp-content/uploads/2023/10/mysqlsampledatabase.zip)；[发布方导入说明](https://www.mysqltutorial.org/getting-started-with-mysql/how-to-load-sample-database-into-mysql-database-server/)。
- 包含客户、商品、产品线、订单、订单明细、付款、员工和办公室 8 张表，业务关系与本系列最接近。
- 练习问题：某客户最近订单、每日订单明细金额、未下单客户、商品销售排行、库存条件更新。订单金额与实际收款分别计算，不混为同一指标。
- 用途：SQL、表设计讨论、事务、锁、日志、复制与恢复；查询优化先用它理解机制，再用 Employees 放大差异。
- 边界：样例规模较小，原始索引可能已经满足部分查询；不以一次计时快慢作为优化结论。商品库存是静态样例值，不假定原订单和付款记录构成完整业务账本；并发库存实验在练习副本中控制初值。
- 已查阅的 [Azure Samples 镜像 SQL](https://github.com/Azure-Samples/mysql-database-samples/blob/main/mysqltutorial.org/mysql-classicmodesl.sql) 使用 InnoDB，含 `quantityInStock` 库存字段，以及旧字符集、SQL mode 与重建表语句。镜像不等于发布方当前压缩包，最终以实际下载文件为准；样例结构用于分析，不直接当作现代建表规范。

### 补充：Employees 员工与薪资历史样例

- 说明：[MySQL 官方数据集介绍](https://dev.mysql.com/doc/employee/en/employees-introduction.html)。
- 获取：[上游 test_db 仓库](https://github.com/datacharmer/test_db)，下载完整仓库，保留根目录下各数据文件；不能只下载 `employees.sql`。
- 官方说明约 400 万条记录、6 张表、约 160 MB 数据；仓库说明导出文件约 167 MB。二者均非导入后的磁盘占用承诺。
- 用途：第 3、4、8 篇比较薪资范围、雇佣日期与部门关联查询，观察全扫描、联合索引、覆盖、排序和估算偏差；索引设计的收益仍取决于查询及分布。
- 最小流程：在解压后的仓库根目录启动 MySQL 客户端，执行 `SOURCE employees.sql;`；导入后运行 `SOURCE test_employees_sha2.sql;`，保留记录数与校验输出。选择普通版，暂不使用分区版导入脚本。
- [上游导入脚本](https://github.com/datacharmer/test_db/blob/master/employees.sql) 会删除并重建 `employees` 数据库，且用相对路径加载多个 dump；仅用于独立练习实例。完成基线校验后再做修改，修改后的库不再期待通过原始校验。
- 上游 README 列有 MySQL 8.4 测试版本，也提示新版客户端的 SOURCE 开关与校验函数差异；实际使用按安装版本核对，本轮不照搬旧教程的 MD5 校验步骤。

### 导入与版本检查

本次只核对来源、文档及可查看的结构脚本，未下载完整数据包，未运行本地数据库或验证导入成功。实际导入时先记录版本、文件来源与校验值，再核对表数量、各表行数、引擎、字符集、索引及会话 SQL mode。

保留原始下载包作为重置来源；修改、加索引、并发和恢复练习使用可重建的练习库。首次打开 SQL 文件先确认目标库和重建行为。Windows 的 MySQL 客户端可按发布方方式用 `SOURCE C:/实际目录/mysqlsampledatabase.sql;` 导入，路径替换为本地解压位置。

旧业务日期不等于 SQL 知识过时：按数据实际时间范围出题，用明确日期区间，避免默认查“最近一个月”得到空集。需要跟进的是数据库版本、导入语法、默认配置和执行机制。

## 贯穿案例与学习方法

主线使用 ClassicModels 的 `customers`、`products`、`orders`、`orderdetails`，对应客户、商品、订单与明细。先选少量记录手算核对，再使用完整样例。原计划的 `users` / `order_items` 是示意名称，实际查询按导入后的表和字段编写。

索引与性能章节按需加入 Employees，减少单纯为凑规模而批量复制订单的工作。表设计和扣库存实验使用自建练习副本；需要控制分布时再生成数据，并保留生成方法。

贯穿任务包括：查询用户最近订单、统计每日成交额、找出未下单用户、按库存条件扣减并创建订单、分析一个慢查询、模拟读到旧数据，以及恢复一次误删。

- 小数据验证语义：空值、重复行、未匹配行和边界时间必须覆盖。
- 大数据观察代价：改变数据量与分布，比较索引前后的计划与实际扫描情况。
- 两个会话验证并发：明确 A、B 的执行顺序、提交时点和预期结果。
- 独立练习实例验证故障与恢复：不在真实数据上演练。

每次学习遵循同一过程：提出问题 → 写下预测与理由 → 精读相关段落 → 运行最小实验 → 对照官方手册解释差异 → 用自己的话整理。

Agent 同时承担教师与写作助手的职责：每次围绕一个问题讲解，先了解用户已有理解，给出练习与必要提示，再根据实际输出追问和纠偏；写作时帮助提炼结论、组织解释、核对证据与版本。用户用自己的话表达后再打磨，讨论和参考草稿先在对话中完成，正文写入按用户具体要求执行。

笔记至少保留：问题与结论、机制解释、可复现步骤与关键输出、一个边界或反例、版本与来源。阅读摘要与待验证推测可以暂存，但不能写成已经验证的结果。

## 系列篇目

### 第一部分：从查询到执行代价

- [ ] **1. 从一个订单查询开始：SQL 在 MySQL 中怎样执行**
  - 主要问题：如何把业务问题写成正确的查询，语句又怎样到达数据？
  - 内容：建表与增删改查；筛选、排序、聚合、连接、子查询只学到能完成练习。串起客户端、Server、优化器、执行器与 InnoDB。
  - 实验：完成最近订单、每日成交额、未下单用户等查询；用小数据核对 JOIN 的重复行与 NULL；看第一份 `EXPLAIN`。
  - 已有素材：执行路径综述；45 讲 01；宝典 12、13 的 SQL 示例；语法缺口查官方教程。
  - 验收：不照抄能写出查询，并指出语法正确与结果正确的区别。
  - 边界：不展开语法大全；执行计划的深入阅读留第 4 篇。旧架构图中的 Query Cache 需要与本轮版本区分。

- [ ] **2. 订单表为什么这样设计：类型、主键与业务约束**
  - 主要问题：一个字段的选择，会怎样影响正确性与后续访问？
  - 内容：金额精度、时间与时区、字符集与排序规则、主键宽度、自增与唯一约束。围绕需求比较设计方案。
  - 实验：比较金额计算结果；切换会话时区观察时间字段；验证大小写比较、重复订单号和事务回滚后的自增空洞。
  - 已有素材：存储结构综述；宝典 01～03、05；45 讲 39。
  - 验收：交代每个关键字段的选择理由、约束和替代方案。
  - 复核：浮点类型与废弃语法分开；金额用 DECIMAL 或最小货币单位整数按需求选择；不直接照搬“一律 BIGINT”“核心表不用自增”等结论。

- [ ] **3. 一次查询究竟读了什么：从数据页到联合索引**
  - 主要问题：为什么加索引能变快，有时又没有帮助？
  - 内容：页与 B+ 树、聚簇与二级索引、回表、覆盖、最左前缀、索引下推，以及索引的写入和空间成本。
  - 实验：围绕“某用户某状态的最近订单”，比较 `(user_id, created_at)` 与 `(user_id, status, created_at)`；比较返回少量字段和整行；改变筛选比例与 LIMIT。
  - 已有素材：索引综述与相关概念；45 讲 04、05、09、11；宝典 08～10。
  - 验收：画出访问路径，解释索引用于定位、过滤、排序、覆盖的不同作用。
  - 复核：跳过中间列不等于整个索引失效；不把旧文章的树高、IO 次数、耗时或“五个索引”当成普遍常数。

- [ ] **4. 有索引为什么还是慢：执行计划、JOIN 与子查询**
  - 主要问题：优化器选择了什么方案，实际代价又是什么？
  - 内容：估算行数与实际行数、循环次数、过滤与排序、统计信息、连接顺序、嵌套循环与 Hash Join、半连接与物化。
  - 实验：构造倾斜数据比较估算与实际；对照 JOIN、EXISTS 与 IN，先核对语义再比较计划；为查询增加索引后再次观察。
  - 已有素材：索引综述；45 讲 10、16、18、34、35；宝典 11～13。
  - 验收：完成一次“观察 → 假设 → 修改 → 复测”的优化，并解释代价减少在哪里。
  - 复核：不沿用“不支持 Hash Join”“子查询一定差”等说法；`EXPLAIN ANALYZE` 会实际运行语句，本轮用于练习库中的 SELECT。

### 第二部分：从并发结果到数据可靠性

- [ ] **5. 同一事务为什么看到不同结果：MVCC 与隔离边界**
  - 主要问题：另一个事务提交后，我究竟能看见什么？
  - 内容：RC 与 RR、读视图建立时点、版本链与 undo、快照读与锁定读、自身修改；解释长事务为何拖住旧版本回收。
  - 实验：先画 A、B 会话时间线，再分别在 RC、RR 下运行读取与更新；比较普通 SELECT 和 `FOR UPDATE`。
  - 已有素材：事务综述、MVCC 概念页；45 讲 03、08。
  - 验收：先预测每次读到的值，再解释实验结果；区分事务开始与一致性读视图建立。
  - 复核：隔离级别的抽象表格不能代替 InnoDB 的具体行为；长事务影响 purge，不等于阻止其他事务写 undo。

- [ ] **6. 只改一行为什么锁住一片：锁范围与并发扣库存**
  - 主要问题：锁在哪里、为什么等，以及怎样避免超卖？
  - 内容：记录锁、间隙锁、next-key lock、唯一约束、MDL、等待与死锁；联系实际扫描路径分析锁范围。
  - 实验：对照唯一键命中、未命中、范围更新和缺少合适索引；用条件更新扣库存；制造反向更新顺序的死锁并查看现场。
  - 已有素材：事务综述、间隙锁概念；45 讲 06、07、19～21、30；40 作为按需延伸。
  - 验收：画出一组实际锁区间，找到阻塞会话；解释原子条件更新、受影响行数、事务边界与重试各自的作用。
  - 复核：用 `performance_schema.data_locks`、`data_lock_waits` 验证；旧版加锁规则与 bug 不能直接外推。“无索引退化表锁”须重审。

- [ ] **7. COMMIT 成功后发生了什么：日志、刷盘与崩溃恢复**
  - 主要问题：数据页还没落盘，为什么提交可以完成？什么条件下仍可能丢数据？
  - 内容：Buffer Pool、WAL、redo、undo、binlog、内部两阶段提交、write 与持久化、组提交；区分进程崩溃、系统故障与存储故障。
  - 实验：检查本机实际参数与 binlog 事件；在独立实例运行已提交和未提交事务，再做一次进程异常终止与重启观察。
  - 已有素材：日志综述；45 讲 02、15、23。
  - 验收：画出一次更新和提交的阶段图，并明确实验只验证了什么。
  - 复核：进程终止不能模拟掉电；一次“没丢数据”不能证明持久性保证。redo 容量按目标版本参数学习，不沿用固定文件数配方。

### 第三部分：把机制用于排查和恢复

- [ ] **8. 慢查询是在算、在等，还是在刷盘：一次完整诊断**
  - 主要问题：用户说“数据库变慢了”，第一步应找什么证据？
  - 内容：扫描代价、锁等待、IO 与刷脏页、临时表与排序、连接和内存；把现象与成因分开。
  - 实验：复用此前的大扫描与锁等待，再增加一个排序查询；从会话状态、慢日志、执行计划与引擎状态分别取证。
  - 已有素材：性能诊断综述；45 讲 12、19、22、29、33；13、14、37 依问题选读。
  - 验收：形成一份有依据的排查过程，说明排除了什么、改了什么、是否复测。
  - 复核：不把“流式返回”扩大为“查询不会用很多内存”；不套用固定命中率、内存比例和参数值；临时表机制按版本查。

- [ ] **9. 写入成功为什么读不到：复制延迟与读写分离**
  - 主要问题：单机一致性为何不能自动延伸到另一台实例？
  - 内容：binlog、relay log、接收与应用、GTID、延迟与读后写一致性；简要比较异步、半同步与故障切换的保证边界。
  - 实验：资源允许时配置两个本地实例，在副本暂停应用线程后写入主库，观察过期读，再恢复应用。资源不足则先做日志与时序推演，实测状态明确留空。
  - 已有素材：复制综述；45 讲 24、26、28；宝典 15、16。
  - 验收：指出事务停在传输还是应用阶段；为订单创建后的查询选择一致性策略并说明代价。
  - 复核：复制命令、线程名称、并行复制默认配置查目标版本；半同步 ACK 不直接等于副本已应用，更不能代替备份。
  - 边界：MGR、Router、完整自动切换和分库分表只列后续入口。

- [ ] **10. 误删后怎样恢复：用一次演练检查整个理解**
  - 主要问题：备份文件存在，是否就意味着数据可以恢复？
  - 内容：一致性备份、binlog 保留、恢复位点与事务边界、恢复后校验；区分备份、复制与高可用。
  - 实验：备份练习库 → 再做正确写入 → 标记一次误删事务 → 恢复到新库 → 重放误删前应保留的事务 → 核对订单、明细和库存。
  - 已有素材：日志综述；45 讲 31；宝典 21。
  - 验收：记录实际恢复耗时、恢复到哪里、哪些数据保住了；用行数、金额汇总及业务关系校验，不只确认命令成功。
  - 复核：确认目标版本备份工具、权限和 DDL 限制；不要把时间点恢复写成无条件“删掉一条日志后全部重放”。
