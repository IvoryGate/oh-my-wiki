# 行锁与表锁

## 核心定义

InnoDB 的锁分为**四个层级**，粒度越细并发度越高，但代价是冲突判断更复杂：

| 层级 | 命令 | 说明 |
|------|------|------|
| 全局锁 | `FLUSH TABLES WITH READ LOCK`（FTWRL） | 全库只读；全备场景应改用 `--single-transaction` |
| 表锁 | `lock tables ... read/write` | 锁住期间不能操作其他表，一般不建议 |
| **MDL（元数据锁）** | 隐式 | DML 与 DDL 互斥，加字段时容易被长查询卡住 |
| 行锁 | 隐式 | InnoDB 特有，粒度最细 |

## 行锁的索引前提

> **行锁是加在索引上的。如果语句没有走索引（或走了全表扫描），行锁会退化为对整张表的锁。**

- S 锁（共享锁）与 X 锁（排他锁）：`lock in share mode` / `for update`
- **两阶段锁协议**：锁在事务执行中陆续加，**commit/rollback 时才释放** → "把最可能造成锁冲突的语句放在最后"
- 锁必须通过索引检索才能精确命中，这是"避免无索引更新"的根源理由

## MDL：加字段的坑（19 篇）

- `alter table` 需要 MDL **写锁**，与已有查询的 MDL **读锁**互斥
- 现象：DDL 不执行也不返回，后面所有语句排队等待
- 定位：`show processlist` → Waiting for table metadata lock；`sys.schema_table_lock_waits`
- 处理：kill 掉持有读锁的长查询
- **纪律：加字段前先确认没有长事务/长查询**

## 行锁的性能账（07 篇）

- "行锁提高了并发，但也带来新的冲突"——**热点行竞争**是主因
- 一致性读只查一行却很慢，可能是**在等锁**（等 MDL / 等 flush / 等行锁），不一定是扫描量大
- 死锁：`innodb_deadlock_detect = on`（默认）；连接数很大时可考虑关闭，改用 `innodb_lock_wait_timeout`（**默认 50 秒**）
- 热点行三类方案：**拆散热点行**（一行拆 10 行 + 并发 select sum）、**改语句形态**（先锁范围再更新）、**串行化**（排队）

## 实践纪律

1. 事务短，尽早提交（锁持有时间 = 事务时长）
2. 更新必须走索引，避免锁退化
3. 删除带 limit，缩小锁范围
4. 大批量更新拆小事务 + 合适的重试与超时
