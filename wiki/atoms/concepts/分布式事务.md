# 分布式事务

## 核心定义

当一次业务操作涉及**不在同一分片的数据**（如 `orders`/`lineitem` 按用户键、`stock` 按商品键）时，必须用分布式事务保证 ACID。

两条路线：**2PC（强一致）** 与 **柔性事务（最终一致）**。

## 2PC 的流程与问题

**流程**：两阶段 **prepare + commit**；**事务协调者**在直连架构中是**业务程序**，在中间件架构中是**中间件**。

**三个问题**：

1. **开销翻倍**——1 次 COMMIT 变成 **2 次 PREPARE + COMMIT**
2. **悬挂事务**——commit 阶段节点宕机 → prepare 成功但没提交，**锁一直不释放**
   - 原文案例：事务 **5136**，PREPARE 状态 **218 秒**，持有 **2 个行锁**
3. **需要人工介入**——`XA RECOVER` 查看并人工提交悬挂事务；`SHOW ENGINE INNODB STATUS` 看未释放锁的 PREPARE 事务

**原文结论**：**"对于海量的互联网业务来说，2PC 的性能是无法接受。"**

## 柔性事务

由**业务层**实现分布式事务，通过**最终一致性**完成——**牺牲一定一致性换取性能**。

- 常见形态：**TCC / SAGA / SEATA / 消息表**
- 手段：**补偿机制**（compensation）
- 难点：**错误逻辑的处理**（正常流程好写，异常分支难写）
- 原文的消息表方案被拆为 **3 个阶段**

## 怎么选

| 场景 | 选择 |
|------|------|
| 海量互联网业务、可容忍最终一致 | **柔性事务** |
| 金融核心、必须强一致、量级可控 | 2PC / XA（并接受开销与悬挂风险） |
| 根本解法 | **单元化闭环**——让业务尽量不跨分片，把问题消解在架构层 |

宝典 25 的补充：中间件的 2PC 性能不满足海量业务，所以支付宝、阿里这类海量业务选择**直连 + 自己实现**；**跨分片 JOIN 也是中间件解决不了的**，同样要靠单元化。

## 与单机事务的衔接

单机侧的原子性靠 [[两阶段提交]]（redo log prepare/commit + binlog）；分布式侧的两阶段是**跨节点**的 prepare/commit——**名字相同、层次不同**，前者解决单机崩溃恢复，后者解决多节点一致性。
