# 幻读

## 核心定义

**幻读**：同一事务内，两次按**同一条件范围查询**，第二次看到了别的事务**新插入**的行，导致行数不同。

与不可重复读的区别：不可重复读针对**同一行内容变化**，幻读针对**范围内行数变化**。

## 幻读带来的三个问题（20 篇）

1. **语义混乱**：读到"不存在的数据"，后续逻辑基于错误事实
2. **数据不一致**：语句级结果与事务级结果对不上
3. **锁的语义被破坏**：原文明说——"锁的设计是为了控制并发，但既然数据都变了，那加锁语义也就被破坏了"

## RR 下的两套对策

原文用一个经典的"先 update 再 select 出现数据不一致"案例展开：

- **快照读**（普通 select）：靠 [[MVCC]] 读旧版本，**不加锁**，天然看不到新插入的行
- **当前读**（update / for update）：读最新版本，必须**加锁圈住范围**——InnoDB 用 **间隙锁 / next-key lock** 锁住"查询到的范围 + 所有间隙"，阻止别的事务插入

> 20 篇用的是**反证假设**："假设不堵住，会出现问题；然后推导出 session A 需要锁整个表所有的行和所有间隙。"（30 篇答疑澄清了读者的误读）

## 结论

- RR 的默认配置下，快照读 + 当前读配合，**常见幻读问题已被覆盖**
- 但"RR 能彻底解决幻读"是过度简化：**不加锁的快照读**看到的仍是旧版本，**非快照的当前读**靠间隙锁防护，而绕过这两者的场景（如先快照读后当前读的混用）仍可能看到不一致——原文建议"事务中需要就用 `select ... for update` 主动加锁"
- 加锁的具体规则见 [[间隙锁]] 与 [[MySQL事务隔离与锁机制]]
