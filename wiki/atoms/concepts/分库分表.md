# 分库分表

## 核心定义

把一张表的数据按**分片键（Shard Key）**水平拆分到多个实例/库/表中。

> **"分布式数据库并不一定要求有很多个实例，最基本的要求是将数据进行打散分片。"**

**分片 = 实例 + 库 + 表 = `ip@port:db_name:table_name`**

## 分片算法

| 算法 | 原文评价 |
|------|---------|
| **RANGE**（按年份/范围） | **"非常糟糕的算法"**——热点集中；唯一好处是**便于 migrate 迁移** |
| **HASH**（如 `o_orderkey % 4`） | **"海量并发的 OLTP 业务，一般推荐用 HASH 的分区算法"** |

- **分片键选择**：电商推荐**用户 ID**，让 `customer` / `orders` / `lineitem` 实现**单元化**（大部分查询按分片键在单分片闭环）
- **命名规则**：四种里**最推荐库名表名都不同**（`tpch01.orders01`），便于扩缩容
- **规模**：**一开始分片数应不少于 1000**
- **扩容**：过滤复制 `replicate_do_db = "tpch01"` + 低峰期切流量

## 主键：用有序全局唯一替代自增

**自增主键不可用**——不同分片会出现相同自增值（`last_insert_id()` 在分布式下不可靠）。

替代：**有序 UUID、发号器、雪花算法**（雪花有时间回溯问题）。

> **"用有序的全局唯一替代自增，是这个时代数据库主键的主流设计标准。"**

## 非分片键查询的三条路

| 方案 | 成本 | 机制 |
|------|------|------|
| **冗余再分片** | — | 冗余表按另一键再打散 |
| **索引表** | **查 2 个分片** | 先查索引表得分片键，再按分片键定位（"回表"式两步） |
| **主键拼入分片键** | **1 次** | 主键编码分片信息：`o_orderkey = string(o_orderkey + o_custkey)` |

补充规则：
- **非唯一二级索引仍需扫所有分片**（如 `o_orderdate` 范围查）
- **全局表**（小、更新少、多用于查询，如 `nation`）→ **每个分片冗余存储**，避免跨分片查询
- **唯一索引必须全局唯一**，替代分片内局部唯一
- 方法论：**空间换时间**——用冗余避免扫所有分片

## 直连 vs 中间件

| | 直连 | 中间件 |
|---|---|---|
| 开销 | 无额外开销 | 单事务耗时上升，**整体吞吐率不变** |
| 复杂度 | 业务要感知分片（**名字服务 + Redis 缓存元数据**） | 模拟 MySQL、**遵循 MySQL 协议**，业务无感 |
| 阈值 | 海量业务（支付宝、阿里用直连） | **高峰期每秒事务 ≤ 1000** 的业务 |

产品（原文）：**ShardingSphere**（2020-04-16 Apache 顶级项目）、**DBLE**（四大行核心业务）、**TDSQL**（500+ 政企金融）。

**共同天花板**：跨分片 JOIN 连中间件也满足不了 → 需**单元化闭环**，跨分片事务只能靠 2PC 或柔性事务（见 [[分布式事务]]）。

## 与分区表的区别

分区表**分的是数据、不是请求**，逻辑上仍是一张表；分库分表是**多张独立表 + 路由**，能真正分摊请求，但引入跨分片查询与事务问题。

> "使用分布式数据库架构是一种折中，你要学会放弃很多，从而才能得到更多。"
