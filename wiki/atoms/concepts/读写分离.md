# 读写分离

## 核心定义

**写只能请求主服务器，读分布到不同从服务器**，由 Load Balance 组件对业务透明地分配请求。

**核心矛盾是过期读**——"在从库上会读到系统的一个过期状态"。原文的定性：**"过期读在本质上是由一写多读导致的。"**

宝典 16 的另一种定性：**"这可能并不是 MySQL 复制的问题，而是你的业务没有根据 MySQL 复制的特点进行设计。"**

## 六种技术方案（45讲 28）

| 方案 | 做法 | 局限 |
|------|------|------|
| **强制走主库** | 请求分类，必须最新的走主库 | 金融类"全部不能过期读"则等于放弃读写分离；**但用得最多** |
| **sleep** | `select sleep(1)` | 0.5 秒也要等 1 秒；超 1 秒仍过期 |
| **判断主备无延迟** | SBM=0 / 位点两组相等 / GTID 两集合相等 | 只证明"**收到**的日志执行完了"，**备库还没收到的那批照样过期** |
| **配合 semi-sync** | 三步 ack 后才返回客户端 | 一主多从中**只保证回 ack 的那个从库** |
| **等主库位点** | `master_pos_wait(file,pos,timeout)` → M / NULL / −1 / 0 | 所有从库都延迟时压力全落主库，需限流 |
| **等 GTID** | `wait_for_executed_gtid_set(gtid_set,1)` → 0/1；5.7.6 起 `session_track_gtids=OWN_GTID` | 同上 |

方案可混合使用。前三种判断的**共同缺陷**：客户端已确认提交、但备库还没收到的事务，任何检测都查不到。

## 路由与降级（宝典 16）

- 引入 **Load Balance**，按权重分配读请求
- **默认权重**：**1%** 读走主机，三台从机各 **33%**
- **兜底**：发生严重主从延迟时，**从机权重 0、主机权重 100%**
- **前提**："从机不能落后主机很多，最好是能准实时数据同步，务必一定要开始并行复制，并确保线上已经将大事务拆成小事务"

## 准确监控延迟

**`Seconds_Behind_Master` 不适合严格判断**（宝典 16 三个原因）：
1. I/O 线程有延迟时**值为 0 但可能已严重落后**（有大事务时）
2. 级联复制最下游**只反映与上一级的延迟**
3. 主从时区不同也不准

**心跳表方案**（更准）：

```sql
CREATE TABLE heartbeat (server_uuid VARCHAR(36) PRIMARY KEY, ts TIMESTAMP(6) NOT NULL);
-- 每 3 秒 REPLACE 一次（event scheduler 调度）
-- 主从延迟 = 从机当前时间 − heartbeat.ts
```

## 与"备库延迟"的关系

读写分离**放大**了延迟的代价（备库被读负载拖慢），而延迟又**制造**了过期读——所以宝典 16 才说"其实是你用错了"：先拆大事务、开并行复制，再谈读写分离设计。
