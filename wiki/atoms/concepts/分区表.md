# 分区表

## 核心定义

分区表把**一张表的数据分成多个物理文件**（1 个 `.frm` + N 个 `.ibd`）存储，对外仍是**一张逻辑表**；引擎层看是 N 个表，Server 层看是 1 个表。

**定性（宝典 14）**："分区表技术不是用于提升 MySQL 数据库的性能，而是方便数据的管理。"——**分区分的是数据，不是请求**。

## 分区类型

- **RANGE**（最常用）、**LIST**、**HASH**、**KEY**、**COLUMNS** 五种分区函数
- RANGE 示例：`PARTITION BY RANGE(YEAR(ftime))`（p_2017 / p_2018 / p_2019 / p_others，`VALUES LESS THAN MAXVALUE`）
- HASH 示例：`PARTITION BY HASH(id) PARTITIONS 4`
- **分区列**："无论选择哪种分区函数，都要指定相关列成为分区算法的输入条件，这些列就叫'分区列'"

## 硬性限制

| 限制 | 后果 / 报错 |
|------|-----------|
| **主键必须包含分区列** | 否则建表失败 |
| **唯一索引必须包含分区列，且只在本分区内唯一** | `ERROR 1503 (HY000): A UNIQUE INDEX must include all columns in the table's partitioning function` |
| **首次访问要访问所有分区** | 非分区列查询扫全部分区：**4 分区 12 次 I/O vs 普通表 4 次** |
| **所有分区共用同一 MDL** | DDL 影响比单表更大 |
| **分区数超 1000 与 `open_files_limit` 默认 1024 冲突** | 建分区表报错 |
| 8.0 禁止建 MyISAM 分区表 | 5.7.17 起 deprecated |

> **口径说明**：两篇分区文章**均未提及外键限制**，也**都没用过"分区裁剪"这个词**——45讲 43 说"必要的分区"，宝典 14 用 `EXPLAIN PARTITIONS` 看 `partitions` 列 + "查询条件都带有分区字段"。不要替原文补充未写的内容。

## 关键机制

- **局部索引**："分区表的索引都是局部，而非全局。也就是说，索引在每个分区文件中都是独立的"
- **分区数不是越多越好**（45讲 43："分区并不是越细越好"）——**单分区一千万行已是小表**
- **引擎实现演进**：**通用分区策略**（每次访问分区都由 server 层控制，"实现上很粗糙，有比较严重的性能问题"）→ **本地分区策略**（InnoDB 内部自己管理，**5.7.9 起**）
- **B+ 树影响有限**（宝典 14）：分区后树高从 4 降 3，**性能提升微乎其微**

## 分区管理操作

| 操作 | 效果 |
|------|------|
| `ALTER TABLE t DROP PARTITION p0` | 删除整个分区（效果类似 drop 普通表） |
| `ALTER TABLE t TRUNCATE PARTITION p0` | **等效 TRUNCATE TABLE**，删除分区数据与索引；**只是一条 DDL 日志，不易造成主从延迟** |
| `EXCHANGE PARTITION ... WITH TABLE t1` | 分区与独立表互换，可配合 LOAD DATA 快速导入/导出 |
| `EXPLAIN PARTITIONS SELECT ...` | 看 `partitions` 列，判断是否只扫了命中分区 |

**时序建议**：**在业务写入前预先规划分区**，不要事后重新分区；RANGE 分区便于按时间清理老数据。

## 什么时候用

- ✅ **单表查询优化到极限仍无法满足，且查询条件能命中分区键**
- ✅ 需要按时间/业务维度**快速清理或归档**老数据
- ❌ 想靠分区提升并发性能——它**不分请求**
- ❌ 无法在分区列上做查询——每次都要扫全部分区

**主键设计**（44 篇的上期答案）：分区要求主键含分区字段 → 联合主键；从利用率看选 **`(ftime, id)`**（多数语句含 ftime，可用**前缀索引**规则少建一个索引）；建议用 InnoDB 并额外加 `KEY id (id)`。也可 `PRIMARY KEY (id, ftime), KEY id (ftime)`。
