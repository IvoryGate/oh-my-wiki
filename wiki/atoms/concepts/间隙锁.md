# 间隙锁

## 核心定义

**间隙锁（gap lock）** 锁住索引记录**之间的间隙**，唯一目的是**阻止别的事务在这个间隙里插入**，从而防止幻读。它不锁记录本身，两个事务可以同时持有同一间隙的间隙锁——**间隙锁之间不冲突**。

## next-key lock

> **next-key lock = 间隙锁 + 行锁**，是一个**前开后闭区间** `(a, b]`。

- InnoDB 加锁的基本单位（默认 RR）
- 间隙由**右侧的值**定义：`(5,10]` 的间隙是 5 到 10
- 原文提示：分析加锁规则时可以按 next-key lock 整体分析，但**具体执行是分成"先加间隙锁、再加行锁"两段**的——死锁案例里 session B 加 next-key lock(5,10] 时，第一步间隙锁成功、第二步行锁才被挡住

## 加锁规则（21 篇：2 原则 + 2 优化 + 1 bug）

> 版本前提：5.x <= 5.7.24，8.0 <= 8.0.13。

**原则**：① 基本单位是 next-key lock；② **访问到的对象**才加锁。

**优化**：
1. **唯一索引**等值查询命中记录 → next-key lock **退化为行锁**
2. 等值查询**不命中** → 向后遍历到的最后一个不满足条件的 next-key lock **退化为间隙锁**

**bug**：RR 下 `select ... where id = 10` 命中唯一索引时，会对**主键 id > 10 的记录错误地加 next-key lock**（原文标注该现象源于历史 bug 93806 类问题）。

## 动态视角（30 篇）

- 锁是**逐个加**的，范围随遍历逐步扩展
- `order by id desc` 这类语句，引擎内部先**按等值查询定位**（找 id=12，没找到但找到了 (10,15) 这个间隙），再向左遍历——"通过树搜索方式定位记录时，用的是等值查询的方法"
- **`delete ... limit N` 会显著缩小锁范围**：循环提前结束，limit 之后的间隙不再加锁 → **"在删除数据的时候尽量加 limit"**

## insert 的特殊情形（40 篇）

- **唯一键冲突**：对冲突记录加 **S 型 next-key lock**（原文指出这是历史 bug 遗留的非直觉行为）
- 插入意向锁（insert intention lock）是间隙锁之间的特殊锁，与 gap lock 交互会产生死锁
- RR 下 insert 的锁在**语句结束**即释放一部分，但要等间隙锁持有者释放

## RR vs RC

切到 RC 后"去掉间隙锁的部分，只剩行锁"；且 RC 在语句结束时释放不满足条件的行锁——**锁范围更小、锁时间更短**（原文补充：外键场景下 RC 仍有间隙锁）。
