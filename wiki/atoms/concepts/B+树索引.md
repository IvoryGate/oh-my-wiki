# B+树索引

## 核心定义

B+ 树是 InnoDB 索引的底层结构：**非叶结点只存 key + 指针，数据（或主键值）只在叶子结点**，叶子结点之间用链表相连——用**矮树高**换**少 IO**，同时天然支持范围扫描与排序。

## 结构演进（04 篇）

**二叉搜索树 → 平衡二叉树 → 红黑树 → B-Tree → B+Tree**。演进的驱动力是：树越高，一次查询的 IO 次数越多。

## 与其他结构的对比（宝典 08）

| 对比项 | B+ 树 | 哈希 | B 树 |
|--------|-------|------|------|
| 等值查询 | O(log n) | **O(1)**（但有哈希冲突） | O(log n) |
| 范围查询 / 排序 | **支持**（叶子链表） | 不支持 | 只能中序遍历 |
| 最左前缀 / 前缀匹配 | **支持** | 不支持 | 有限 |
| 树高 | **更低** | — | 非叶结点也存数据 → 更高 |

宝典 08 给出的 B 树对比口径：读取次数 **4 次 vs 3 次**、读取量 **62500KB vs 1000KB**。

## 层高：两套示例口径

InnoDB 页大小 **16KB**；非叶结点每项 = 主键（BIGINT 8B）+ 指针（6B）= 14B → 约 **1100 个键值对**。

- **宝典 08**：2 层 = 1100 × 16 = **17600 条**；3 层 = **1936 万条**；4 层 = **212 亿条** → 原文结论 **3~4 层**
- **45讲 04**：按 N≈1200 估算 → 2 层 ≈ **144 万行**，3 层 ≈ **20 亿行**；查询 = 2 次 + 1 次 IO，**10ms 内**

> 两套数字的**参数假设不同，结论一致**：真实业务的表基本落在 3~4 层内，IO 次数可控。引用时务必带上口径来源。

**全表扫描的代价**（宝典 08）：无索引时 5 亿数据 × 4KB/IO = **200GB 流量、3 分钟**。

## 页分裂

**触发条件**（两个都要满足）：当前相邻页空间不足 + 新记录比当前页最大值大（插入到中间才分裂）。

**代价**：页利用率**下降约 50%**。

**减少手段**：① 自增主键 ② 用完页全部空间 ③ 主键列设 `NOT NULL`——这也是"自增主键优于随机主键"的结构性理由。
