# MySQL事务隔离与锁机制

> 03 → 08 → 20 → 21 → 30 → 40 是一条不断细化的线：先给隔离级别的定义，再拆穿"隔离的假象"，最后给出可操作的加锁规则。

## 一、隔离级别：四层语义

原文把隔离定义为"一个事务执行过程中的数据，对其他事务的可见性"，并给出四种级别：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|-----------|------|
| 读未提交（Read Uncommitted） | 有 | 有 | 有 |
| 读提交（Read Committed, RC） | 无 | 有 | 有 |
| 可重复读（Repeatable Read, RR，**默认**） | 无 | 无 | 有 |
| 串行化（Serializable） | 无 | 无 | 无 |

- **脏读**：读到别的事务未提交的数据
- **不可重复读**：同一事务内两次读同一行结果不同
- **幻读**：同一事务内两次按同一条件范围查询，行数不同

**长事务的代价**：事务提交前，InnoDB 必须保留该事务的**回滚日志**（undo log）——"即便事务没有发生更新，它或许只是个查询，但 InnoDB 一样要为它生成 read view，然后在事务提交之前，不管发生了什么，都不允许其他事务更新 undo log"。所以**事务尽快提交**是基本纪律，必要时将查询改成 `select ... for update`（加锁）反而更安全。

## 二、快照读与当前读

- **快照读**（普通 `select`）：读的是 MVCC 快照，不加锁
- **当前读**（`select ... for update` / `lock in share mode` / `update` / `insert` / `delete`）：读的是**最新版本**，必须加锁
- **一致性读**：不加锁的读，依赖一致性读视图（见 [[MVCC]]）
- **两阶段锁协议**：锁在事务开始后陆续加，**直到 commit/rollback 才统一释放**——"如果你的事务中需要锁多个行，要把最可能造成锁冲突、最影响并发度的语句放在最后"

原文提示：RR 级别下事务的更新行为其实会**读到别的事务已提交的最新值**（"当前读"），这也是 08 篇要拆解的"隔离与不隔离"的矛盾点。

## 三、锁的层级与代价

### 四层锁（06、07、19 篇）

| 层级 | 命令 | 场景与坑 |
|------|------|---------|
| 全局锁 | `FLUSH TABLES WITH READ LOCK`（FTWRL） | 全库只读；备库做全备时要加 `--single-transaction` 避免它 |
| 表锁 | `lock tables ... read/write` | 锁期间不能操作其他表，一般不建议用 |
| **MDL（元数据锁）** | 隐式加 | 加字段的 DML 需要 MDL **写锁**，与长查询的 MDL **读锁**互斥 |
| 行锁 | 隐式加 | **只有通过索引检索，才能使用行锁**；否则退化为表锁 |

**MDL 导致的"卡死"现场（19 篇）**：
- 现象：`alter table` 不执行也不返回，后面所有查询全部排队
- 定位：`show processlist` 看 Waiting for table metadata lock；`sys.schema_table_lock_waits` 可直接看到等锁的语句
- 处理：`kill <session_id>` 掉持有 MDL 读锁的长查询
- 教训：**给表加字段前先确认没有长事务/长查询**

### 行锁的性能账（07 篇）

- "行锁虽能提高并发效率，但也带来了新的冲突"——热点行竞争是主因
- `innodb_thread_concurrency = 0`（默认，不限制并发）；有界时用 `innodb_thread_concurrency` + `innodb_thread_concurrency_delay` 控制
- 死锁：`innodb_deadlock_detect = on`（默认）；连接数大时可考虑关掉，改用 `innodb_lock_wait_timeout`（**默认 50 秒**，业务侧重设）
- **热点行更新的三类方案**：把行锁改成语句锁（`select ... for update` 先锁范围）、拆散热点行（如将一行拆成 10 行 + 并发 select sum）、改成队列串行化
- 原文出处："update ... set id = id + 1" 这种语句在高并发下，锁会沿主键顺序逐个等——把 update 拆成"读取最新值再更新"并不解决问题，核心是**减少锁的持有与等待范围**

### 一致性读也可能是"慢查询"（19 篇）

只查一行却慢，原文给了三类现场：**等 MDL 锁 / 等 flush / 等行锁**——慢不一定是扫描量大，可能是**在等锁**。

## 四、加锁规则速查（21、30 篇）

原文规则（2 原则 + 2 优化 + 1 bug）：

> **前提**：只适用于 5.x 系列 <= 5.7.24、8.0 系列 <= 8.0.13（原文版本提示）。

**两个原则**：
1. 加锁的基本单位是 **next-key lock**（前开后闭区间 `(a, b]`）
2. **查找过程中访问到的对象**才加锁

**两个优化**：
1. **唯一索引**上的等值查询，next-key lock **退化为行锁**（且查不到记录时退化为间隙锁）
2. **等值查询无匹配**时，向后遍历的最后一个不满足条件的 next-key lock **退化为间隙锁**

**一个 bug**：`RR` 下 `select ... where id = 10` 命中唯一索引后，若主键 id 是**递增插入**的，等值查询语义上不会碰到后面的记录，但 InnoDB 会对主键 id>10 的记录**错误地加上 next-key lock**

**动态观点（30 篇）**：锁是"逐个加"的，不是一次性圈定范围——
- 间隙由**右侧的值**定义（`(5,10]` 的间隙是 5 到 10）
- `order by id desc` 定位时，引擎内部先**按等值查询定位**（找 id=12，没找到但找到间隙），再向左遍历
- `update` = 删除旧版本 + 插入新版本，所以 update 的锁与 insert/ delete 的行为相关
- **delete 的 limit**：加了 `limit N` 后循环提前结束，锁范围明显缩小 → **"在删除数据的时候尽量加 limit"**

**insert 的特殊加锁（40 篇）**：
- `insert ... select`：对 select 的表加锁（当前读语义）
- **唯一键冲突**：对冲突记录加 **S 型 next-key lock**（而非 X 锁，原文标注这是历史 bug 93806 的遗留）
- `on duplicate key update`、自增 id 回收等场景的锁行为各异
- insert intention lock（插入意向锁）是间隙锁之间的特殊锁，与 gap lock 的交互见死锁案例

**RR vs RC 的锁差异**：切到 RC 后"去掉间隙锁的部分，只剩行锁"；RC 还会**在语句结束时就释放不满足条件的行锁**——"读提交隔离级别下，锁的范围更小，锁的时间更短"。

## 五、贯穿主线的实践纪律

1. 事务尽可能短，别用事务做远程调用
2. 避免无索引更新（退化表锁）与大事务
3. 高并发更新热点行要**拆热点 / 缩范围 / 串行化**
4. 加字段前先检查长查询，防 MDL 卡死
5. 删除尽量带 limit，缩小锁范围
6. 排查锁问题：`show engine innodb status` 看死锁、`information_schema.innodb_trx` 看事务、`sys.schema_table_lock_waits` 看 MDL
