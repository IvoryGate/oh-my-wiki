# MySQL执行路径与基础架构

> 一条 SQL 走过的路：连接器 → 查询缓存 → 分析器 → 优化器 → 执行器，以及藏在权限读取时机里的那些"反直觉"。

## 分层：Server 层与存储引擎层

MySQL 分为 **Server 层**和**存储引擎层**两部分：

- Server 层包括**连接器、查询缓存、分析器、优化器、执行器**等，涵盖大多数核心服务功能与所有内置函数（日期、时间、数学、加密等），所有跨存储引擎的功能都在这一层实现——存储过程、触发器、视图等
- 不同的存储引擎共用同一个 Server 层；InnoDB 自 **MySQL 5.5.5** 起成为默认引擎

这条分层是后续所有机制的公共地基：redo log 是 InnoDB 特有的、binlog 是 Server 层的，权限表在 mysql 库、判断却走内存——都由分层决定。

## 执行链路的五个环节

### 1. 连接器：建连接、认证、读权限

- 经典 TCP 握手后用用户名密码认证；认证通过后**到权限表里查出你拥有的权限**，此后这个连接里的权限判断逻辑都依赖于此时读到的权限
- **权限生效时机的关键结论**："一个用户成功建立连接后，即使你用管理员账号对这个用户的权限做了修改，也不会影响已经存在连接的权限"
- 空闲连接由 `wait_timeout` 控制，默认 **8 小时**
- 连接复用可用 `mysql_reset_connection`（**MySQL 5.7+**）：不重连、不重新验证权限

### 2. 查询缓存：建议不用

- 以 key-value 缓存（key=语句，value=结果），命中直接返回
- **失效过于频繁**：只要对一个表有更新，该表所有查询缓存都被清空 → 更新压力大的库命中率极低
- 按需使用：`query_cache_type = DEMAND`，语句用 `SQL_CACHE` 显式指定；仅适合长期不更新的静态表（如系统配置表）
- **MySQL 8.0 彻底删除该功能**

### 3. 分析器：词法分析 + 语法分析

词法分析识别关键字、表名、列名；语法分析按语法规则校验。"不知道你是谁、要做什么"的错误都出在这里。

### 4. 优化器：选索引、定 join 顺序

表里有多个索引时决定用哪个；多表关联时决定连接顺序。同样的逻辑结果可以有多种执行方案，效率不同，优化器负责择一。（选错索引的问题在 [[MySQL索引体系与查询优化]] 展开）

### 5. 执行器：权限校验 + 调引擎接口

- 执行前先判断对该表有没有执行权限（命中查询缓存时在返回结果处校验；查询也会在优化器之前调用 precheck 验证权限）
- 打开表，按引擎定义调用引擎接口；无索引时逐步遍历、每行取出来用 where 过滤

## 权限体系：为什么 grant 之后不用 flush privileges

**42 篇把 01 篇"权限读取时机"的结论展开成了内存结构层面的解释**：

| 权限类型 | 存储位置 | 内存结构 | 已建连接是否立即生效 |
|---------|---------|---------|------------------|
| 全局权限 | mysql.user 表 | `acl_users` 数组，权限位**拷贝进线程对象** | 否，对已连接无效 |
| db / 表 / 列权限 | mysql.db 等表 | `acl_dbs`、`column_priv_hash` 是**全局结构，所有线程共用** | 是 |

- `flush privileges` 的作用是"以数据表中的数据为准，将全局权限内存数组重新加载一遍"——只在**磁盘表与内存不一致**时才需要（如直接 UPDATE 了权限表）
- 用 `grant` 命令改权限时会同时更新内存，所以**无需跟着 flush privileges**
- 生产告诫："如果一个用户有所有权限，一般就不应该设置为所有 IP 地址都可以访问"

## 视角：从业务出发设计 MySQL（宝典开篇）

宝典作者姜承尧的核心主张是**站在业务全链路角度**而非单点功能看 MySQL：

- 理论上自增 INT 做主键没问题，但站在双 11、春节红包的角度，**INT 类型做核心业务主键非常不可取**
- 复制技术能搭高可用架构，但**数据库是有状态的，切换可能很慢——不一定非要在数据库层完成高可用**，可以结合业务设计
- "数据库学到最后，要与业务紧密结合，站在业务的角度，全流程地进行思考"

## 学习路径（45讲 开篇与心路历程）

- **主线**：事务、索引、锁；方法是"点 → 线 → 面"，构建知识网络（结束语："路径千万条，实践第一条；原理说不清，双手白费劲；知识没体系，转身就忘记"）
- **推荐书**：只选一本就选《高性能 MySQL》第三版
- **DBA 与开发融合**："开发要了解数据库原理，DBA 要了解业务和开发"；体力活（搬服务器、搭库、切换）已有自动化，价值转向**主动诊断系统**
- **提高 SQL 效率**：多写 SQL 培养感觉——写之前就知道大概率是全表扫描还是索引扫描、要不要回表
