# 分布式数据库与分库分表

> 宝典的递进链：什么叫分布式（22）→ 怎么分片（23）→ 分片后索引怎么设计（24）→ 用直连还是中间件（25）→ 把分片思想推到全链路（26）→ 跨分片事务怎么办（27）。

## 一、什么叫分布式数据库（22）

**定义**："把数据分散存储在不同物理位置的数据库。"

**三层架构**（须**计算与存储分离**）：

| 层 | 职责 |
|----|------|
| **计算层** | 单机数据库中的 SQL 层——权限检查、路由访问、计算结果；**可有多个**（因元数据独立存于元数据层） |
| **元数据层** | 记录集群有多少存储节点及其 IP、端口等元数据 |
| **存储层** | 存放数据，与计算层在同一台服务器上甚至同一进程 |

- **中间件**遵循 MySQL 协议，按元数据路由到各**分片（Shard）**
- **分片 = 实例 + 库 + 表 = `ip@port:db_name:table_name`**
- **每层各自高可用**：中间件无状态、元数据有副本、分片做主从切换
- 优势：**Scale Out 线性提升**，单分片宕机只影响 **1/N** 数据

> 金句："分布式数据库的可用性对比单机会有很大提升，单机数据库要实现 99.999% 的可用性或许很难，但是分布式数据库就容易多了。"

## 二、怎么分片（23）

**分片键（Shard Key）**："用户可通过这个字段进行数据的水平拆分。" 电商场景**推荐用户 ID**，让 `customer` / `orders` / `lineitem` 实现**单元化**。

| 算法 | 评价（原文） |
|------|------------|
| **RANGE**（如按 `YEAR(o_orderdate)`） | **"非常糟糕的算法"**——热点集中；唯一好处是**便于 migrate 迁移** |
| **HASH**（如 `o_orderkey % 4`） | **"海量并发的 OLTP 业务，一般推荐用 HASH 的分区算法"** |

**四条分库分表规则，最推荐第 4 种**：**库名与表名都不同**（如 `tpch01.orders01`），便于扩缩容。

**规模建议**：**一开始分片数应不少于 1000 个**（原文提及网传阿里某核心业务分片数 10000；反例是 32、64 这类小分片数）。

**扩容**：搭复制架构并用**过滤复制** `replicate_do_db = "tpch01"` 只回放分片所在库，**低峰期切流量**。

> 金句："分布式数据库并不一定要求有很多个实例，最基本的要求是将数据进行打散分片。"

## 三、分片后的索引设计（24）

**主键**：**自增主键不可用**——不同分片会出现相同自增值（`last_insert_id()` 在分布式下不可靠）。替代方案：**有序 UUID、发号器、雪花算法**（雪花有时间回溯问题）。

> 金句："用有序的全局唯一替代自增，是这个时代数据库主键的主流设计标准。"

**非分片键查询的三条路**（24 篇核心）：

| 方案 | 查询成本 | 说明 |
|------|---------|------|
| **冗余再分片** | — | 冗余表按另一个键再打散 |
| **索引表（回表式）** | 查 **2 个分片** | 先查索引表拿分片键，再按分片键定位数据——**两步两条 SQL** |
| **主键拼入分片键** | **1 次** | 主键编码分片信息，如 `o_orderkey = string(o_orderkey + o_custkey)`，查询 `o_orderkey = '1000-1'` |

- 索引表示例：`idx_orderkey_custkey`；查询 `SELECT * FROM orders WHERE o_orderkey = 1` 拆成 step1 查索引表取 `o_custkey`、step2 `WHERE o_custkey = ? AND o_orderkey = 1`
- **非唯一二级索引仍要扫所有分片**（如按 `o_orderdate` 范围查）
- **全局表**（如 `nation`）：无分片键、小、更新少、多用于查询 → **在每个分片中冗余存储**，避免跨分片查询
- **唯一索引须全局唯一**，替代分片内的局部唯一

**空间换时间**：用冗余（冗余表 / 索引表 / 主键编码分片信息）避免扫描所有分片。

## 四、直连还是中间件（25）

| | **直连分库分表** | **分布式中间件** |
|---|---|---|
| 性能 | 无额外开销，性能好 | 单事务耗时上升（**但整体吞吐率不变**） |
| 业务复杂度 | 业务需感知分片，用**名字服务 + Redis 缓存元数据** | 模拟一个 MySQL、**遵循 MySQL 协议**，屏蔽分片 |
| 2PC 能力 | 由业务程序当协调者 | 中间件的 2PC 性能不满足海量业务 |
| 适用 | **海量业务**（支付宝、阿里用直连） | **高峰期每秒事务 ≤ 1000 的小业务** |

**产品**（原文提及）：**ShardingSphere**（**2020-04-16** 成为 Apache 顶级项目）、**DBLE**（用于四大行核心业务）、**TDSQL**（服务 **500+** 政企金融机构）。

**共同天花板**：大数据量跨分片场景**连中间件也满足不了 JOIN 需求**——中间件层会增加单事务耗时，业务需**单元化闭环**，跨分片事务只能靠 2PC 或柔性事务兜底。

> 金句："使用分布式数据库架构是一种折中，你要学会放弃很多，从而才能得到更多。"

## 五、全链路条带化（26）

**条带化（striping）**："把连续数据分割成等大数据块，分别写入阵列中不同磁盘"（RAID 0 的思路）。

**关键洞察**：**只分数据库是不够的**——上层服务也要作为条带的一部分跟着分片拆分：

- 1 个大订单服务 → 拆成多个小服务，**各只访问自己分片的数据**
- 三个好处：**安全校验本分片、性能更好、可用性更好**
- **多活三步走**：分布式改造 → 分片主库放不同机房 → **业务条带化部署**
- 宕机切换时**服务与库一起切换**，避免跨机房访问

相关概念：**单活架构**（所有分片在一个机房，其他机房只读、无法写入）vs **多活架构**（不同地理位置都能提供**实时读/写**服务——"'活'指实时读/写而非只读"）。

> 金句："全链路的设计思想，要将上层服务也作为条带的一部分进行处理。"

## 六、分布式事务：要不要用 2PC（27）

**场景**：跨维度事务——`orders` / `lineitem`（用户键）与 `stock`（商品键）不在同一分片 → 必须分布式事务。

**2PC 流程**：两阶段 **prepare + commit**，**事务协调者**在直连时是**业务程序**、在中间件时是**中间件**。

**三个问题**：
1. **开销翻倍**：1 次 COMMIT 变成 **2 次 PREPARE + COMMIT**
2. **悬挂事务**：commit 阶段节点宕机 → prepare 成功但没提交，**锁未释放**（原文案例：事务 **5136**，PREPARE 状态 **218 秒**，持有 **2 个行锁**）
3. 排查手段：`XA RECOVER` 查看并**人工提交**悬挂事务；`SHOW ENGINE INNODB STATUS` 看未释放锁的 PREPARE 事务

**原文结论**：**"对于海量的互联网业务来说，2PC 的性能是无法接受。"** → 海量业务改用**柔性事务**（TCC / SAGA / SEATA / 消息表），由业务层实现、靠**补偿机制**达到最终一致性，**牺牲一定一致性换取性能**；难点在**错误逻辑的处理**（原文消息表方案拆为 **3 个阶段**）。
