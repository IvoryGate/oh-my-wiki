# MySQL复制与高可用架构

> 分工：**复制负责同步，套件负责切换**——"MySQL 复制技术本身不能实现 failover 的功能"（宝典 19）。45讲从数据正确性切入，宝典从架构与组件切入，两侧几乎不重叠。

## 一、复制的三步流程（45讲 24）

前置：备库先 `change master`（设 IP、端口、用户名、密码、**起始位置 = 文件名 + 日志偏移量**）→ `start slave`。

| 步骤 | 原文表述 | 线程 |
|------|---------|------|
| **写入** | 主库执行内部事务的更新逻辑，**同时写 binlog**（T1 = 主库执行完成） | — |
| **传输** | 备库与主库维持长连接，主库按备库给的位置读取 binlog 发送；备库写到本地文件 = **中转日志 relay log**（T2 = 备库接收完） | 主库 **Dump 线程** → 备库 **I/O 线程** |
| **重放** | 备库**读取中转日志、解析出命令并执行**（T3 = 备库执行完成） | **SQL / Worker 线程** |

**总原理**："binlog 的特性确保了在备库执行相同的 binlog，可以得到与主库相同的状态。"

**主备延迟 = T3 − T1**，即同一个事务在备库与主库执行完成的时间差。

## 二、格式与一致性（24 篇核心）

`binlog_format` 三种格式对复制正确性的决定性影响：

| 格式 | 记什么 | 复制正确性 |
|------|--------|-----------|
| **statement** | SQL 原文 | 可能主备走不同索引（`delete ... limit 1` 例）→ **可能不一致**；线上仍用 statement"基本上就可以认为这是一个不合理的设置" |
| **row** | 真实变更的行（Table_map + Delete_rows） | "传到备库去的时候，就肯定会删除 id=4 的行"；且**让不一致更容易被发现** |
| **mixed** | MySQL 自动判断 | 可能引起不一致就用 row；`now()` 这类依赖上下文的语句额外记 **`SET TIMESTAMP=...`** 约定返回值 |

**推论**：恢复数据要把**整段 `mysqlbinlog` 输出**交给 MySQL 执行，不能拷出某条 statement 单独执行（执行结果依赖上下文）；statement 格式还会自动补 `use 'test'`。

**循环复制（双 M）**：靠 binlog 中的 **server id** 判重——两库 server id 必须不同，收到与自己相同 server id 的日志直接丢弃。不完备场景（27 篇）：运行中改 `server_id`；A/A'/B 迁移用 `CHANGE MASTER TO IGNORE_SERVER_IDS=(...)` 处理。

## 三、延迟的四类成因（45讲 25 / 26）

1. **备库机器性能比主库差**——20 个主库放 4 台、备库集中 1 台，且备库设"非双 1"（`innodb_flush_logs_at_trx_commit=2`、`sync_binlog=1000`）→ 现多改为**同规格机器、对称部署**
2. **备库压力大**——主库写、备库兼做读与后台分析，查询耗 CPU 拖慢回放 → 一主多从分担读，或把 binlog 输出到 Hadoop 等外部系统做统计
3. **大事务**——主库必须等事务完成才写 binlog；一次性 delete 太多、**大表 DDL**（计划内建议 gh-ost）
4. **备库并行复制能力不足**——单线程回放不够快 → 持续低于主库生成速度 → **小时级延迟，压力高时永远追不上**

**宝典 16 的量化**：删除当月 1 亿条 → 可能产生 **100G binlog**，磁盘每秒写 100M → **至少等 1000 秒**才能提交。对策：① 把 `DELETE` 改成 `DROP TABLE/PARTITION`（流水表按时间分表）；② 拆小事务 `DELETE ... LIMIT 1000`（还可多线程并发删）；③ 主库没建索引也会让简单操作变慢，**备库回放同样耗时**。

**版本底线（宝典 16）**：**要彻底避免延迟，数据库至少升级到 5.7**——之前的回放是单线程（5.6 是库级单线程）。

**"45° 斜线"型延迟**（26 篇答案）：大事务（含大表 DDL）；或备库起了长事务堵住主库 DDL 的应用。

### 并行复制

**两条顺序约束**（26）：① 更新同一行的两个事务必须分到同一 worker；② 同一事务不能拆开。

- **coordinator**：就是原来的 `sql_thread`，不再直接更新数据，只负责读中转日志与分发
- **worker**：真正更新日志的线程，个数由 `slave_parallel_workers` 决定（45讲建议 **8~16**，32 核）
- `slave-parallel-type = DATABASE | LOGICAL_CLOCK`
- `binlog-transaction-dependency-tracking = COMMIT_ORDER | WRITESET | WRITESET_SESSION`
- **writeset**：事务涉及更新的每一行算出的 hash 集合，**两事务 writeset 无交集即可并行**

**宝典 16 的两种模式与落地配置**：

| 模式 | 行为 | 局限 |
|------|------|------|
| `COMMIT ORDER` | 主库怎么并行，从库就怎么并行 | 主库单线程每次插 1000 条 → 从库仍单线程回放，**仍有延迟** |
| `WRITESET` | 更新记录不冲突就可并行 | **"虽然主机是单线程，但从机可以是多线程并行回放"→ 几乎没有延迟** |

```sql
binlog_transaction_dependency_tracking = WRITESET
transaction_write_set_extraction      = XXHASH64
slave-parallel-type                   = LOGICAL_CLOCK
slave-parallel-workers                = 16
```

## 四、判断延迟：三种方法与共同缺陷（28 篇）

1. **`seconds_behind_master` 是否为 0**
2. **对比位点**：`Master_Log_File` = `Relay_Master_Log_File` 且 `Read_Master_Log_Pos` = `Exec_Master_Log_Pos`
3. **对比 GTID**：`Retrieved_Gtid_Set` = `Executed_Gtid_Set`（配合 `Auto_Position=1`）

②③ 比 ① 更准确。**但三者有共同缺陷**：只证明"备库**收到**的日志都执行完了"，仍存在一批"客户端已收到提交确认、备库还没收到"的日志 → **照样会过期读**。

**SBM 的三条缺陷（宝典 16）**：I/O 线程有延迟时值为 0 但可能已严重落后（有大事务时）；级联复制最下游只反映与上一级的延迟；主从时区不同也不准。

> **口径差异**：45讲把 SBM 当作可用的延迟指标（时钟差会通过连接时的 `SELECT UNIX_TIMESTAMP()` 自动扣掉，不构成缺陷），宝典则明言它"用于严格判断主从延迟并不合适"——宝典补充的是 45讲未提及的缺陷，属**互补而非直接反驳**。

**更准的方法（宝典 16）：心跳表**——主从延迟 = 从机当前时间 − `heartbeat.ts`（每 3 秒 `REPLACE` 一次，用 event scheduler 调度）。

## 五、读写分离的坑：过期读

**过期读 = "在从库上会读到系统的一个过期状态"**。"过期读在本质上是由一写多读导致的。"

**45讲 28 的六种方案**：

| 方案 | 要点 | 局限 |
|------|------|------|
| **强制走主库** | 请求分类，必须最新的走主库 | 金融类全不能过期读则等于放弃读写分离；但**用得最多** |
| **sleep** | `select sleep(1)` | 0.5 秒也要等 1 秒；超 1 秒仍过期 |
| **判断主备无延迟** | 见上节三法 | 备库未收到的事务查不到；高峰位点更新快会"过度等待" |
| **配合 semi-sync** | 三步 ack 后才返回客户端 | 一主多从中只保证回 ack 的那个从库 |
| **等主库位点** | `master_pos_wait(file,pos,timeout)` → M / NULL / −1 / 0 | 所有从库都延迟时压力全落主库，需限流 |
| **等 GTID** | `wait_for_executed_gtid_set(gtid_set,1)` → 0/1；5.7.6 起返回包带 GTID（`session_track_gtids=OWN_GTID`） | 同上 |

**宝典 16 的视角不同**："这可能并不是 MySQL 复制的问题，而是你的业务没有根据 MySQL 复制的特点进行设计。"

- 引入 **Load Balance** 对业务透明，按权重分配读请求
- **默认权重**：**1%** 读走主机、三台从机各 **33%**
- **兜底**：严重主从延迟时**从机权重 0、主机权重 100%**
- 前提："从机不能落后主机很多，最好是能准实时数据同步，务必一定要开始并行复制，并确保线上已经将大事务拆成小事务"

## 六、复制类型（宝典 15 / 18）

**四种类型**：

| 类型 | 机制 | 适用 |
|------|------|------|
| **异步复制** | Master 不关心 Slave 是否收到，性能最好 | 能容忍数据丢失的业务（原文例：微博） |
| **半同步（有损，5.7 之前）** | WAIT ACK 发生在**事务提交之后** | Master 宕机时 **Slave 会丢失最后一批提交的数据** |
| **半同步（无损，5.7）** | WAIT ACK 发生在**事务提交之前**，未收到 ACK 前事务对用户**不可见** | **"电商的核心订单业务、银行、保险、证券……务必使用无损半同步复制"** |
| **多源复制** | N 个 Master → 1 个 Slave | 多实例同步到一台做统计（OLAP） |
| **延迟复制** | `CHANGE MASTER TO master_delay = 3600` | 防误操作：设延迟一天 = 拥有 1 份 24 小时前的快照 |

**半同步插件配置**（宝典 15）：`plugin-load="rpl_semi_sync_master=semisync_master.so;rpl_semi_sync_slave=semisync_slave.so"` + `rpl-semi-sync-master-enabled=1` + `rpl-semi-sync-slave-enabled=1`。

**金融口径**：强同步 = `rpl_semi_sync_master_wait_point = AFTER_SYNC`。

**crash safe 六个必配参数**（宝典 15）：

```
gtid_mode = on
enforce_gtid_consistency = 1
binlog_gtid_simple_recovery = 1
relay_log_recovery = ON
master_info_repository = TABLE
relay_log_info_repository = TABLE
```

> 金句："请确认上述参数都已配置，否则任何的不一致都不是 MySQL 的问题，而是你使用 MySQL 的错误姿势所致。"

## 七、高可用：三大架构与容灾分级（宝典 17 / 18）

**定义与度量**：高可用 = 系统提供无故障服务的能力；基础是**冗余 + 故障转移（Failover）**，消除**单点故障（SPOF）**。

- **99.99% = 1 − 52.56 / (365×24×60)**（每年宕机不超过 **52.56 分钟**）
- 云厂商 99.995% → **26.28 分钟**/年
- **建议线上目标不低于 99.995%**

**数据库高可用比无状态服务难的三点**：数据持久化（有状态）、容量大导致 Failover 时间长、金融场景要求数据完全不丢。

**三大架构方案**（宝典 17）：

1. **基于数据层**——靠复制技术，Master 宕机转移到 Slave；为让服务无感知需引入 **VIP（Virtual IP）**，宕机时 VIP 漂移到新主。三大难点：① 保障数据一致性（用无损复制）② 发现主库宕机 ③ 故障转移逻辑（②③由高可用套件完成）
2. **基于业务层**——写失败直接写另一台。前提是**状态可修改**：订单主键 `PK = 有序UUID-服务器编号`，编号 1 失败改用编号 2 → **"跳单"**；查询由主键中的服务器编号直接路由。类似 NoSQL 的 KV 访问，可结合 Memcached Plugin
3. **融合架构**——业务层 + 数据层结合。不同编号订单存不同 DB，并用**部分复制**（只同步指定 DB）；常态下**双活都可写**，宕机时写可跳单、读不受影响

**容灾分级**（宝典 18）：

| 级别 | 架构 | 关键参数 |
|------|------|---------|
| 机房内 | 单机房多节点 | 无损半同步 |
| **同城** | **三园区 / 一地三中心 / 两地三中心** | 机房网络延迟 **≤ 5ms**；`rpl_semi_sync_master_wait_for_slave_count = 1` |
| **跨城** | **三地五中心** | 三城距离 **> 200km**、延迟 **> 25ms**；**ACK = 2** |

同城容灾的坑：两机房互联未考虑网络抖动 → 抖动会把事务提交 hang 住，所以**务必三园区**。完整架构还要：2 个异步复制节点做读写分离 + 1 个异步**延迟备机**做误删除恢复，主库向 4 个从库发日志 → **务必配置万兆网卡**。

跨城 25ms 影响大，一般只用于**读多写少**场景（如用户中心）。

### 数据兜底：数据核对（宝典 18）

解决两件事：**业务逻辑上一致**（业务对不对）+ **主从之间数据一致**（从机数据安全、可切）。

- **业务逻辑核对由业务同学编写**：库存消耗 = 订单明细总和；在途快递 + 已收快递 = 已下快递总和
- **主从核对由数据库团队负责**：写独立核对服务，**不依赖复制本身**（属逻辑核对）
- 找"最近变更记录"两思路：① 每张表有 `last_modify_date`，按此过滤逐条比；② 扫描最近 binlog 筛选更新过的表和主键（难但不查库）
- **复核机制**：核对中记录又变了就复核，"多复核几次……如果复核多次不一致，那么大概率，主从数据就已经是不一致的了"

## 八、切换与套件选型（45讲 25/27 + 宝典 19）

**两种切换策略**（45讲 25）：

| 策略 | 做法 | 代价 |
|------|------|------|
| **可靠性优先**（推荐） | 先等 `seconds_behind_master = 0` 再切流量（SBM < 5 秒是前置检查） | **存在不可用窗口** |
| **可用性优先** | 不等同步直接切、可读写 | 几乎无不可用，但**可能数据不一致**，仅日志类库可用且需事后补数据 |

**异常切换**：主库掉电时只能等 SBM=0，系统完全不可用。

**位点与 GTID**（45讲 27，GTID 为 **MySQL 5.6** 引入）：
- `gtid_mode=on` + `enforce_gtid_consistency=on` + `master_auto_position=1` 自动找位点
- **GTID 协议要求日志完整**，缺 binlog 直接拒绝；位点协议由备库决定、不做完整性判断
- 跳过错误：`sql_slave_skip_counter=1` 或 `slave_skip_errors=1032,1062`（1062 唯一键冲突、1032 删除找不到行）

**透明接入**（宝典 19）：
- **VIP**：虚拟 IP 可绑任意服务器，failover 后漂移 → **仅限同机房同网段**
- **DNS 名字服务**：跨机房用域名
- **"上层服务一定要做好错误重试的逻辑，否则就算启用 VIP，也无法实现透明的切换。"**

**套件三选一**：

| 方案 | 机制 | 规模建议 |
|------|------|---------|
| **MHA** | Manager + Node 两组件，**ssh 通信**（有安全风险、效率不高） | **MySQL 服务器不超过 20 台** |
| **Orchestrator** | "MHA 的升级版"，HTTP 接口 + 元数据库；但到 MySQL 仍是 ssh | 仍建议小规模 |
| **自研平台** | HTTP API + 元数据库 + Manager + 每台 MySQL 的 **agent**，**BP 协议 / grpc** 通信替代 ssh | 成千上万节点；"才能真正实现数据库管理的无人驾驶" |

## 九、InnoDB Cluster（宝典 20）

**= MGR 集群 + MySQL Shell + MySQL Router**

- **MGR**：MySQL **5.7** 推出的**基于状态机**的同步机制，插件启用；**"不要简单认为它是一种新的数据同步技术，而是应该把它理解为高可用解决方案"**
- 同步不用复制技术，而用 **GCS（Group Communication System）协议**——**类似 Paxos**，**大部分节点收到日志才能提交** → **节点数须为奇数**
- 启用时 MySQL **新开一个端口**做同步 → 比半同步更快
- 两模式：**单主**（自动 Failover 与 Primary Election，不用部署额外 Agent）/ **多主**（提交时做行冲突检测，冲突自动回滚）
- **三条限制**：① 仅 InnoDB 且**每表必须有主键**；② **最多 9 个节点**；③ 一个节点网络抖动就影响整集群（Paxos 对网络极敏感）
- **多主最佳实践**："每个节点写各自的数据库，比如节点 1 写 DB1，节点 2 写 DB2"才能线性提升
- **多主自增**：`group_replication_auto_increment_increment` **默认 7**、起始值 = server-id；3 节点实测结果 **1、8、16、17、22**——"自增值不一定是严格连续的，而仅仅是单调递增的"→ 核心业务表建议用**有序 UUID**
- **MySQL Router**："定位是一种轻量级的路由转发，**而不是一个数据库中间件**"；官方建议与客户端以 **sidecar** 方式部署
- 建议在 **MySQL 8.0** 使用；金句："这种高可用解决方案大概率会成为下一代金融场景的标准数据库高可用解决方案。"

## 十、两栏互补关系（无硬冲突）

| 议题 | 45讲 | 宝典 |
|------|------|------|
| 半同步 | 只讲三步 ack | **区分有损/无损**，给 `AFTER_SYNC` |
| 延迟成因 | 四类（含机器/压力） | 两类（大事务 + 单线程回放），给量化算例 |
| `seconds_behind_master` | 当作可用指标 | **"不准确"**，给 3 缺陷 + 心跳表 |
| 读写分离 | **过期读** + 6 技术方案 | **Load Balance 权重 + 兜底降级** |
| crash safe 参数 | 未展开 | **6 个必配参数** |
| 数据核对 / 容灾分级 / MGR | 无 | 三者独有 |
| 版本前提 | 5.6（GTID）、并行复制演进 | **硬底线 5.7**、InnoDB Cluster 建议 8.0 |
