# MySQL存储结构与表设计

> 宝典的主线是"从业务出发做类型与表设计"，45讲的主线是"存储引擎如何实现这些设计"——两边在自增主键与分区表上正面交汇。

## 一、表结构设计：范式与主键（宝典 05）

**三范式**：一范式属性不可分、二范式解决部分依赖、三范式解决传递依赖。

原文的工程化结论：**实际只需要两条——每张表必须有主键 + 消除冗余**。范式不是教条，OLAP 与在线业务都可做**反范式设计**（JSON 类型普及后在线业务也能反范式）。

**核心表为什么不该用自增主键**（宝典 05 给了 6 条理由）：值可回溯、并发冲突、**非全局唯一**、暴露业务量、MGR/分布式场景冲突。

**UUID 的问题**：按时间位**逆序存储**，前 4 个字节随时间"随机"变化、**非单调递增** → 插入产生**离散 IO**。宝典 05 的解法：MySQL 8.0 `UUID_TO_BIN` 可把 36 字节缩为 **16 字节**，性能优于自增；分布式主键可用**时间字段 + 随机码 + 业务信息**组合。

> **口径冲突（必须并列引用）**：`innodb_autoinc_lock_mode=1` 下多 value INSERT 的自增锁释放时机，**45讲 39 与宝典 05 正面矛盾**（前者：不会等语句执行完成才释放；后者：该条 SQL 执行完成后才释放）。宝典该结论部分依赖图片表格，图不可读——两说并存，按版本实测为准。

## 二、字段类型选择（宝典 01–04）

| 类型 | 原文要点 |
|------|---------|
| **数字**（01） | 自增主键**一律 BIGINT 而非 INT**（INT 约 42 亿，1000 万/天约 420 天到顶）；到上限报 `ERROR 1062`，**不会重置为 1**；8.0 前自增值不持久化、重启回溯；unsigned 相减报 `ERROR 1690`（需 `NO_UNSIGNED_SUBTRACTION`）；**Float/Double 8.0.17 起警告并将废弃**；**金额用 BIGINT 按分存**，别用 `DECIMAL(8,2)` |
| **字符串**（02） | `CHAR(N)` 的 **N 是字符不是字节**；8.0 默认 **utf8mb4**（之前 Latin1），emoji 否则 `ERROR 1366`；多字节字符集下 CHAR 与 VARCHAR 底层都是变长，可统一用 VARCHAR；collation 后缀 **`_ci` 不区分大小写 / `_cs` 敏感 / `_bin` 二进制比较**；改列必须 `ALTER TABLE ... CONVERT TO CHARSET`；有限值列 8.0.16+ 用 `CHECK`，之前用 ENUM + `STRICT_TRANS_TABLES` |
| **日期**（03） | DATETIME **8 字节**（5.6+ 支持毫秒 `DATETIME(6)`）；TIMESTAMP **4 字节**但**上限 2038-01-19 03:14:07**；带毫秒 TIMESTAMP 7 字节；默认时区每次调 `__tz_convert()` **需加锁** → 海量并发下性能抖动；须显式 `time_zone="+08:00"`；**推荐 DATETIME**，核心表加 `last_modify_date ON UPDATE` |
| **JSON**（04） | 5.7 引入、8.0 解决更新日志瓶颈（推荐 **8.0.17+**）；有**自己的存储格式、可建索引**，不是大字符串；取值 `JSON_EXTRACT` / `->>`；**虚拟列 + 函数索引**检索；8.0.17 起 **Multi-Valued Indexes** 配 `MEMBER OF` / `JSON_CONTAINS` / `JSON_OVERLAPS`；**忌存余额、姓名、身份证**，宜存静态少改数据 |

金句（宝典 04）："最容易犯的误区就是将类型 JSON 简单理解成字符串类型。"

## 三、空间回收与表压缩

### 删了一半，文件为何不缩（13）

- `innodb_file_per_table` **MySQL 5.6.6 起默认 ON**，只有 ON 才谈得上回收
- **delete 只是把记录位置或数据页标记为"可复用"，磁盘文件大小不变** → 形成**空洞**
- 空洞来源不只是 delete：**随机插入导致页分裂、更新索引值**同样产生空洞

**重建表的算法演进**（13 篇的核心时间线）：

| 版本 | 能力 |
|------|------|
| 5.5 之前 | 拷贝表，**非 Online，阻塞 DML** |
| 5.6 起 | **Online DDL**，记 row log；MDL 写锁可提前退化为读锁 |
| 后续 | **inplace ≠ Online**（8.0 加全文/空间索引仍不 Online） |

**两条实务约束**：
- **1TB 的表需要 1.2TB 磁盘**才够 inplace（临时文件要额外空间）
- `analyze table` = 重算统计信息；`optimize table` = 重建 + 重统计；**大表推荐 gh-ost**（原文只提了 gh-ost 这个名字，未给原理/参数）

### 压缩（宝典 06）

- 页默认 **16K**；**行压缩与表空间压缩都不可行，只用页压缩**
- `COMPRESS`：`ROW_FORMAT` + `KEY_BLOCK_SIZE`，5.7 之前可用，压缩比约 **50%**
- COMPRESS 的代价：缓冲池要同时存 **8K + 16K 两页**，**QPS 下降约 30%**
- **TPC（Transparent Page Compression）**：**5.7 推出**，利用文件系统**空洞（Punch Hole）**、4K 对齐，**侵入小于 20%**
- LinkBench 实测：**13432 → 10480 → 18882 QPS**
- `ALTER` 只改元数据，**必须 `OPTIMIZE TABLE` 才会真正压缩整表**

金句："压缩并不意味着性能下降，或许能额外提升性能。"

## 四、count() 为什么慢（14）

- **MyISAM** 存了总数直接返回；**InnoDB 因 MVCC 要逐行判断可见性**
- 优化器会**遍历最小的那棵索引树**
- `show table status` 的 **`TABLE_ROWS` 是采样，误差 40%~50%**
- **Redis 缓存计数会丢更新**，且读写顺序调换仍不一致——根因是"两个不同的存储构成的系统，不支持分布式事务，无法拿到精确一致的视图"
- 正解：**数据库计数表 + 事务**，得到一致性视图
- 效率：`count(1)` 不取值快于 `count(主键)`；`count(*)` 被专门优化为不取值

> 原文的"效率排序"完整表达式在剪藏文件中被截断，**完整排序原文未明确**，可确认的只有结论：**尽量使用 `count(*)`**。

## 五、临时表与内存表（36 / 37 / 38）

### 为什么临时表可以重名（36）

- 临时表**只有创建它的 session 可见**，session 结束自动删除，可用任意存储引擎
- frm 文件放临时目录，命名前缀 **`#sql{进程id}*{线程id}*序列号`**（`select @@tmpdir` 查看目录）
- 5.6 及之前建 `.ibd`，**5.7 起改用临时文件表空间**
- 内部标识 **`table_def_key` = 库名 + 表名 + server_id + thread_id** → "它们的 table_def_key 不同，磁盘文件名也不同，因此可以并存"
- **复制规则**：`binlog_format=row` **不记临时表操作**；statement/mixed 才记；`drop table` 记入 binlog 时被改写加 **`/* generated by server */`**

### 什么时候用内部临时表（37）

- `union` 会建内存临时表靠唯一约束去重，`union all` 不需要
- `group by` 出现 `Using temporary + Using filesort` 就是在用它
- **`tmp_table_size` 默认 16M**，超限转**磁盘临时表**（默认 InnoDB）
- 不需要排序就加 **`order by null`**，省掉一次 filesort
- 5.7 用 **generated column** 建有序索引可免临时表
- `SQL_BIG_RESULT` 直接用 sort_buffer 数组排序

原文的三件套比喻：**"join_buffer 是无序数组，sort_buffer 是有序数组，临时表是二维表结构。"**

> `max_heap_table_size` 在本批文章中**均未出现，原文未明确**——内存临时表上限只提了 `tmp_table_size`。

### 还要不要 Memory 引擎（38）

- InnoDB 是**索引组织表**，Memory 是**堆组织表**、主键为 **hash 索引**
- 内存表**不支持 Blob/Text**，`varchar(N)` 被当成 `char(N)`
- 范围查询用不上 hash 主键索引，可 `add index using btree`
- **只支持表锁**：一张表更新会堵住全部读写
- **重启全清空**；主从双 M 场景下备库重启会向主库发 `DELETE` 清表
- **结论："我建议你把普通内存表都用 InnoDB 表来代替"**，唯一合理用途是内存临时表

## 六、自增机制（39 / 45）

### 自增 id 为什么不连续（39）

三个原因：**唯一键冲突、事务回滚、批量申请的消耗**（1→2→4 式递增浪费）。

- 自增值存储：MyISAM 在**数据文件**，InnoDB 在**内存**；**8.0 才记入 redo log 持久化**
- 5.7 及之前重启取 `max(id)+1` → **自增值会回溯**
- `auto_increment_offset` / `auto_increment_increment` 默认均为 1
- `innodb_autoinc_lock_mode`：**5.1.22 引入，默认 1**；原文建议 **mode=2 且 `binlog_format=row`**，批量插入含 `load data`
- **"才只保证了自增 id 是递增的，但不保证是连续的"**

**备库为何不会因自增不一致**（44 篇）：`binlog_format=statement` 下，insert 前固定写 **`SET INSERT_ID=n`** → 备库用同一自增值；**row 格式**的 Write row event 直接写了每行所有字段，天然无此问题。

### 各类 id 用完会怎样（45）

| id | 上限与行为 |
|----|-----------|
| 表自增值 | 到 **4294967295** 后不再增长，再插**报主键冲突** → 应用层改 `bigint unsigned` |
| `row_id`（无主键表的隐藏主键） | **6 字节**，0~2⁴⁸−1 后**归 0 循环覆盖数据** |
| `Xid` | 来自 `global_query_id`，重启清零，仅同一 binlog 内唯一 |
| `trx_id` | 只读事务不分配，显示值 = 指针地址 + 2⁴⁸；`max_trx_id` 持久化，**归 0 会引发持续脏读**，TPS 50 万约 **17.8 年** |
| `thread_id` | 4 字节归 0，靠唯一数组防重复 |

金句（45）：**"覆盖数据，就意味着数据丢失，影响的是数据可靠性；报主键冲突，是插入失败，影响的是可用性。"**

> 剪藏文件中 `2³²−1`、`2⁴⁸−1` 等上标已丢失为 `232-1` 等形式，此处按文中"4 个字节/6 个字节/8 个字节"语义还原。

## 七、复制一张表的四种方法（41）

| 方法 | 要点 |
|------|------|
| **mysqldump** | 配 `--single-transaction`、`--add-locks=0` 导出 INSERT；`source` 是客户端命令 |
| **into outfile / load data** | 受 **`secure_file_priv`** 限制（空 / 路径 / NULL）；不覆盖同名文件；load data 分 local（客户端文件）与非 local |
| **物理拷贝** | 6 步：**discard → flush for export → cp → unlock → import**；`flush` 后整表只读直到 `unlock tables` |
| **`insert into ... select`** | 走 SQL 执行，受回表与日志影响 |

**结论："物理拷贝的方式速度最快，尤其对于大表拷贝来说是最快的方法"**——但前提是**全表复制、两边都是 InnoDB、能登录主机**。

## 八、分区表（43 + 宝典 14）

详见 [[分区表]]。本篇要点：

- **分区"分的是数据，不是请求"**——宝典 14 的定性：**"分区表技术不是用于提升 MySQL 数据库的性能，而是方便数据的管理"**
- **45讲 43 的工程警告**：单分区一千万行已是小表，**"分区并不是越细越好"**；首次访问要访问所有分区；**分区超 1000 与 `open_files_limit` 默认 1024 冲突**
- 45讲 43 记录了引擎实现的演进：**通用分区策略**（server 层管理，性能问题严重）→ **本地分区策略**（InnoDB 自管，5.7.9 起）
- 所有分区**共用同一 MDL** → DDL 影响比单表更大

## 九、SQL 还是 NoSQL（宝典 07）

三种访问方式（**底层都是表、都存 InnoDB**，利于收敛技术栈）：

1. **SQL**
2. **Memcached 协议**（MySQL **5.6+** 插件，默认端口 **11211**，映射到 `innodb_memcache.containers`）——绕过 SQL 解析，实测**快 54.33%**、CPU 开销低 20%
3. **X Protocol**（**5.7+**，默认端口 **33060**，需单独装 MySQL Shell）

与 MongoDB 相比**仅不支持数据分片**，但可用 CTE、窗口函数。
