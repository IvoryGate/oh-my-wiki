# MySQL索引体系与查询优化

> 承接链：04（B+ 树基础）→ 05（联合索引/回表/下推）→ 09（普通 vs 唯一）→ 10（选错索引）→ 11（前缀索引）→ 16/17（order by）→ 18（Q1/Q2 对比）→ 34/35（join）。宝典侧：08（排序的艺术）→ 09（索引组织表）→ 10（组合索引）→ 11（CBO）→ 12（JOIN）→ 13（子查询）。

## 一、为什么是 B+ 树

结构演进（04）：**二叉搜索树 → 平衡二叉树 → 红黑树 → B-Tree → B+Tree**。

核心差异：
- **B+ 树叶子结点才存数据**，非叶结点只存 key + 指针 → 一页能放下更多索引 → 树更矮
- **叶子结点间有链表** → 支持范围扫描与排序；哈希索引不支持范围/排序/最左前缀/前缀匹配
- InnoDB 页大小 **16KB**；主键 BIGINT（8B）+ 指针（6B）= 14B → 非叶结点约 **1100 个键值对**

**树高层级的两套口径**（不同文章的示例参数不同，都能自洽）：

| 口径 | 参数 | 结果 |
|------|------|------|
| 45讲 04 | N≈1200（一个索引节点管理的行数） | 2 层 ≈ **144 万行**，3 层 ≈ **20 亿行**，3 层查询 = 2 次 + 1 次 IO，**10ms 内** |
| 宝典 08 | 页 16KB / 14B per key → 1100 键值对 | 2 层 17600 条、3 层 **1936 万条**、4 层 **212 亿条**；原文给 **3~4 层**、50 亿行 4 次 IO |

对比 B 树（宝典 08）：**B 树非叶结点也存数据** → 树更高、IO 更多（原文对比读取次数 4 次 vs 3 次）；B 树只能中序遍历，B+ 树靠叶子链表范围扫。

无索引的代价（宝典 08）：全表扫描 **5 亿数据 × 4KB/IO = 200GB 流量、3 分钟**。

**页分裂**（宝典 08）：页满**且**新记录比当前页最大值大时插入中间 → 分裂，**利用率下降约 50%**。减少手段三条：**① 自增主键 ② 用完页全部空间 ③ 主键列 NOT NULL**。这也是"自增主键更好"的结构性理由（呼应 45讲 39 自增主键不连续）。

## 二、聚簇索引、二级索引与回表

- **聚簇索引**：主键索引树的**叶子结点是整行数据**——数据文件本身就是一个按主键构造的 B+ 树，即"索引组织表"（宝典 09：万物皆索引）
- **二级索引**：叶子结点存**主键值** → 取整行要回主键索引查一次 → **两棵 B+ 树**
- **回表**（05）：= 主键索引与二级索引**各执行一次 B+ 树查询**；回表后主键索引访问的**页是随机的**，磁盘最优情形 4KB/次、随机 IO 约 0.4ms/页
- **覆盖索引**：查询结果字段都在索引里 → 不回表，`EXPLAIN` 的 **`Using index`** 即覆盖索引

05 篇的对照实验（18 篇复用同一组数字）：
- Q1 取 `id`：走索引不回表 ≈ **40ms**（只有一次随机 IO）
- Q2 取 `age`：回表 ≈ **21ms**（按数据页缓存而非按行，所以比"回表 4000 行 × 1ms"的直觉估算低）

**索引下推 ICP**（05，MySQL 5.6 引入）：联合索引 `(name, age, sex)` + `name LIKE '张%' AND age=10 AND sex='M'`——不支持时先按 name 取全部再回表过滤；支持时**在索引层就判断 age/sex**，减少回表次数。即"把过滤下推到存储引擎层"。

## 三、联合索引的四条规则

1. **最左前缀**：`(a,b,c)` 能用 `a=`、`a= AND b=`、`a= AND b= AND c=`；**不能用** `b= AND c=`、`a= AND c=`（"如果用了 b 或 c 但没用 a，索引就失效"）。04 补充**索引复用**：`(a,b)` 相当于同时拥有 `(a)` 和 `(a,b)`
2. **覆盖优先**：能用覆盖索引就别 `select *`——`select *` 必回表，filesort 也常因此触发
3. **前缀索引与区分度**（11）：`count(distinct left(email, N))` 测区分度，达 **85%** 即可；代价有二——**不能用于 ORDER BY/分页**、定长变**变长**导致回表变慢 → 口诀**"宁可索引长一点"**
4. **字段顺序三口诀**（11）：**区分度大的在前、字段小的在前、查询频率高的在前**

## 四、索引该建多少、普通还是唯一

- **普通 vs 唯一**（09）：**查询**性能差异可忽略（按页读取）；**更新**上普通索引可用 **change buffer**，唯一索引必须做唯一性校验
- **change buffer**：只对**二级索引**有效、对主键索引无效、**唯一索引不使用**；`innodb_change_buffer_max_size` 默认 **50**（占 buffer pool 50%）；"离索引页越远，merge 越节约 IO"
- **数量**（宝典 10）：**单表索引不建议超过 5 个**——每个索引都要维护 B+ 树，磁盘/内存开销与写入效率都在付出代价；1000 字段的表只给 5 个字段建索引（45讲 18 口径）
- 每个索引对应独立文件，**索引越多磁盘占用越高**（18）

## 五、索引选错：CBO、统计信息与直方图

**MySQL 默认优化器是 CBO（Cost-Based Optimizer，基于代价的优化器）**（宝典 11）：基于表统计信息（扫描行数、磁盘 IO）估算代价，**不考虑"索引越多越好"**，只选代价最低的执行计划——所以"有索引却没用上"是常态，`EXPLAIN` 是必查动作。

**"选错"的定性**（10 篇做了一次事实核查）：**属于正常现象，不是 MySQL 的 bug**——优化器掌握的统计信息不够准，或代价模型本身估算偏了。

**四条对策**（10）：
1. `ANALYZE TABLE t` 重新分析统计信息
2. `SELECT ... FORCE INDEX(index_name)` 强制指定——**只对单条 SQL 生效**
3. 改写 SQL（改变语义或加 `/*+ ... */` hint）
4. **增加或删除对应索引**，让优化器"看得见"更优解

**直方图**（10）：
- `ANALYZE TABLE t UPDATE HISTOGRAM ON col WITH N BUCKETS` / `DROP HISTOGRAM ON col`
- 统计信息存放在 **`mysql.column_stats`** 表；`SHOW HISTOGRAM FOR TABLE users` 查看
- 宝典 11 示例：5001 行中 F=2450（49%）、O=2425（48.5%）、P=126（2.5%）
- 原文反直觉提示：加直方图后某个查询的索引选择**可能由正确变为错误**——直方图改变了代价估算

**统计信息持久化**（18）：
- `innodb_stats_persistent = ON`（默认）
- `innodb_stats_persistent_sample_pages` = **20**（持久化的采样页数 N）、`innodb_stats_transient_sample_pages` = **8**（未持久化的 M）
- 宝典 11 补充：`innodb_stats_auto_recalc` 开启后更新 **10%** 行即自动重算（8.0 动态采样）

**CBO 的代价参数**（宝典 11）：`mysql.server_cost` 表（`constant_cost=1`、`row_evaluate_cost=0.2` 等）与 `engine_cost` 表可调；实测通过补索引 `idx_status_createdat(status, createdat)`，`cost` 从 **18.98 → 6.65 → 2.94**，执行时间 **12.35s → 1.04s**，`Extra` 去掉了 `Using filesort`。

**判断口径**：`EXPLAIN` 中 **`type=ALL` + `Extra=Using filesort`** = 没有合适索引可选；`type=ALL` 即全表扫描。MySQL 8.0 还支持 **`EXPLAIN ANALYZE`** 看真实执行数据。

## 六、order by：三条执行路径

1. **索引直接有序**——走索引就不排序（"排序的艺术"，宝典 08）
2. **sort_buffer 内存排序**
3. **临时文件归并**（磁盘）

**全字段排序 vs rowid 排序**（16）：
- 全字段排序：整行进 sort_buffer，排完直接返回
- rowid 排序：只放**排序字段 + id（6 字节）**，排完再回表——省内存但多一步
- 分界参数 **`max_length_for_sort_data`**（16 篇示例设 16，超过即改用 rowid 排序）
- **`sort_buffer_size` 不是单条 SQL 独占**，并发语句共用
- 内存不够就用临时文件：trace 中 `number_of_tmp_files` = **12**（全字段）/ **10**（rowid）/ **0**（内存装下）

**优先队列优化**（16）：`order by ... limit N` 时用堆只取 N 行，N 较大时仍需全量排序。原文口径为"MySQL 4.0+ 及后续版本"。

**`select *` 是常见破绽**：即使排序字段有索引，`select *` 需回表 → 仍走 filesort。

**随机消息的两种优化**（17 + 宝典 10）：
- `ORDER BY RAND()` 要生成随机数并排序，扫描 **20003 行**（表 20000 行），排序比较 **20000×20000** 次，**无法用索引**
- 方案 A（17）：业务层生成随机主键——`SELECT MAX(id)` 定位 + `LIMIT`
- 方案 B（17）：加随机列/时间列排序，让取消息接口少一次随机 IO
- 方案 C（宝典 10）：建**组合索引** `(createdat DESC, userid DESC)` 替代 RAND()，"优化到毫秒级响应"

## 七、join：算法与优化

**四种写法**（宝典 12）：INNER JOIN（交集）、LEFT JOIN（左全 + 右匹配否则 NULL）、RIGHT JOIN；**MySQL 不支持 FULL OUTER JOIN**。

**执行顺序**（宝典 12）：`ON → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`；`EXPLAIN` 输出中 **`id` 列决定执行顺序**。

**三种算法**（35）：Nested Loop Join / Simple Nested Loop Join / **Block Nested Loop Join**（用 `join_buffer_size`，**默认 256k**）。

**优化四条**（35）：
1. **小结果集驱动大结果集**（"小表驱动大表"）
2. **优先 JOIN，避免子查询**（优化器对 IN 子查询改写能力弱）
3. **优先基于索引 join**——被驱动表的关联字段必须有索引
4. 用 `EXPLAIN` 分析

**量级数据**（34）：3 万条场景 NLJ **5.6s**、BNL **75s**、Hash **3.7s**——但原文同时强调**"MySQL 不支持 Hash Join"**（该测试在其他数据库上做）；`WHERE t2.gift IS NOT NULL` 这类条件**写在被驱动表**上，"差别很大"。

**BNL 的替代方案**（35）：10 亿次判断耗时 **1 分 11 秒**；改成**临时表 + hash** 后**少于 1 秒**（原文描述的"临时表方案"，即用一次性临时表模拟 hash join）。

**join 的取舍**（34）：能写 join，但**不应该在单实例上做破坏设计的行为**——"无论在索引列上创建多少个索引，进行 JOIN 操作都可能会慢"；关联无索引、结果集无关联时应**拆表**或多写一列冗余。

## 八、子查询：优化器的死穴（宝典 13）

- 分类：标量/行/表子查询；WHERE/HAVING/FROM/EXISTS 位置；**相关 vs 非相关**
- **三类优化器弱项**：
  1. **WHERE 中的子查询**：优化器"没有任何改写能力"，只能暴力逐行循环——`IN (子查询)` 例：t2 有 10000 行、t1 逐行比对 → **5002ms**，改 JOIN 后 **12ms**（**400 多倍**）
  2. **ORDER BY 中的子查询**：每行执行一次，扫描行数被"放大"，中间结果用不上索引
  3. **GROUP BY 中的子查询**：无法用临时表/索引优化
- **EXISTS vs IN**：EXISTS 返回**布尔值**（只问存在与否），执行顺序**先外层后子查询**；IN 返回结果集
- **定论**：查询场景两者差异不大；**增删改场景子查询性能不如 JOIN**，且内外层表可能"不同步"（外层旧数据、内层已更新）有安全隐患 → **优先 JOIN**

## 九、两处版本口径冲突（重要）

同一件事在两栏给出相反结论，**建页与引用时必须带版本前提**：

| 议题 | 45讲口径 | 宝典口径 | 处理 |
|------|---------|---------|------|
| **Hash Join** | "MySQL 不支持 Hash Join，最好也不要使用"（34） | "MySQL 8.0 支持 Hash Join"（12） | 45讲以 5.6/5.7 为主，宝典以 8.0 为主；**按版本分别成立** |
| **索引选错定性** | "属于正常现象，非 bug"，给 4 条对策 + 直方图（10） | 强调 CBO 成本优先、补索引 + 统计自动重算（11） | 不冲突，是**同一问题的两条解法线**（统计 vs 直方图） |

## 十、实践清单

1. 建索引前算**区分度**，字段顺序按三口诀排
2. 能覆盖就别 `select *`，能 `limit` 就别全量排序
3. 删除带 `limit`，深分页改"延迟关联"或用组合索引
4. **每条慢 SQL 先 `EXPLAIN`**：`type=ALL` / `Using filesort` / `Using temporary` 都是信号
5. 索引选择异常先 `ANALYZE TABLE`，再考虑 FORCE INDEX 或补/删索引
6. 单表索引数控制在 5 个以内，热点表尤其如此
7. 大表 join 优先"小驱动大 + 被驱动表建索引"，MySQL 8.0 前可用临时表 + hash 替代 BNL
8. 子查询在 WHERE/GROUP BY/ORDER BY 中尽量改写成 JOIN
